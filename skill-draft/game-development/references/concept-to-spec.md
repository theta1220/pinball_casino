# コンセプトから実装へ

既存の操作・制約・プレイを確認し、コンセプトを「プレイヤーが何をして、何を感じるか」の一文にする。世界観や機能一覧だけで済ませない。

本ユーザーのゲーム設計では「行動の選択→結果の観察→学習→選択を変えて反復」を最優先する。入力値だけが変わっても、結果が強制補正されて同じなら選択にならない。発射は低・中・高の入力で実際の到達点・速度・失敗と再試行を比較する。リールは報酬用の絵柄へ強制停止させず、回転の初期条件と減速から停止位置を決め、停止絵柄をゲーム側が評価する。乱数への置換だけで選択を取り戻したと判断しない。どの入力がどの観測可能な差を生むか仕様とテストへ明記する。

面白さは主観的な仮説として扱う。判断できる選択肢、リスク、結果を予測できる情報、技能が結果に影響する箇所、再挑戦したい理由を具体化する。「爽快」「中毒性」だけで説明しない。実測やプレイ観察がない成功率・楽しさを断定しない。

仕様書にはコンセプト、核となる循環、短中長期目標、操作、状態遷移、数値、報酬、失敗、持越し、演出と情報、例外処理、検証項目を必要な範囲で含める。各追加機能にコンセプト上の役割を対応させ、役割がない複雑さを足さない。

ルールと演出を分離し、報酬は一度だけ確定する。抽選演出中の落球、最終球、ポーズ、連打、リスタートを仕様化する。ランダム性を採用するなら技能との関係と確率を明記する。既存記録と採点基準が変わるときは記録の互換性も決める。

球や回転体の停止が結果条件なら、進入時や任意のタイマー終了時に報酬を先取りしない。受入・減速・安定停止・結果確定・排出を分け、速度と安定継続時間で停止を判定する。確定した結果から反応を一度だけ発火する。

仕様は開発資料へ置き、ゲーム画面には遊ぶための状態と反応だけを出す。説明文を追加しないという依頼を、進捗まで見えなくする意味に拡大解釈しない。

実装後は仕様の各ルールをコード・テスト・観察へ対応付ける。自動検証でルールの正しさ、実操作で理解しやすさと操作感を分けて確認する。面白さの評価には目標を認識できたか、狙いを変えたか、失敗原因が伝わったかを観察し、未検証の仮説を明記する。
